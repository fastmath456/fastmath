# 빠른수학 서버 구성·개발 루프 초안

작성일: 2026-10-09 · 기준 UI 커밋: `531aac4` · 프로젝트: `/Users/sangkun/nocoders/quick-math`

**추천 출발점은 기존 Next.js에 필요한 API만 추가하고, 관리형 DB·인증·파일 저장소를 연결하는 것이다.** 아래 서비스와 API·데이터 구조는 제안이며 확정 명세가 아니다. 이번 작업은 초안 작성까지다. 서버 구현, 서비스 생성, 실제 메일·결제·영상 연결, 배포는 수행하지 않았다.

## 1. 현재 상태와 범위

| 구분 | 현재 상태 | 서버 단계에서 할 일 |
| --- | --- | --- |
| 앱 | Next.js 16.4.0, React 19.3.0, App Router, TypeScript strict, npm | 기존 버전·설정 유지 |
| UI | PC 화면 1차 구현과 MSW 표시 검증 | 승인된 화면에 실제 데이터 연결; 모바일 제외 |
| 데이터 | TanStack Query → 최소 fetch 함수 → MSW → fixture | 조회 함수와 응답 매핑부터 실제 API로 전환 |
| 실제 처리 | 인증·DB·저장·결제·환불·이용권·영상 서비스 없음 | 실제 결과를 확인한 뒤에만 성공 화면·상태 표시 |
| 남은 UI | 미리보기 모달 배치, 재설정 토스트 위치, 조회 로딩 표현 확인 필요 | 서버 연동 대기와 구분; 디자인 근거 없이 새 UI 추가 금지 |

React Compiler·Cache Components와 CSS Modules를 유지한다. UI 내부 상태는 React, HTTP 상태는 TanStack Query로 관리한다. Zustand에는 서버 데이터를 복제하지 않는다. 현재 전역 store가 없으므로 서버 도입만을 이유로 만들지 않는다.

현재 실행 명령은 `npm run dev -- --hostname 127.0.0.1`, URL은 `http://127.0.0.1:3000`이다. UI 작업에서 lint·타입 검사·빌드가 통과했고, 이번 다섯 UI 커밋의 각 스냅샷도 `next typegen`·`tsc --noEmit`을 통과했다. 이는 실제 서버 연동 검증 결과가 아니다.

## 2. 추천 구성

| 역할 | 제안 | 선택 근거·결정할 사항 |
| --- | --- | --- |
| 웹·API | 기존 Next.js의 `src/app/api/**/route.ts` | 별도 서버 앱 없이 현재 조회 함수와 연결; 호스팅·리전·예산은 미정 |
| DB·인증 | Supabase PostgreSQL·Auth 후보 | 회원·상품·주문 관계를 DB로 관리하고 인증을 직접 제작하지 않음 |
| 파일 | Supabase Storage 후보 | 프로필 이미지와 유료 PDF의 접근 정책을 분리 |
| 결제 | Toss Payments 결제창 후보 | 별도 결제 페이지를 임의로 추가하지 않고 기존 구매 동선과 연결 가능한지 확인 |
| 영상 | 기획의 Vimeo 연동 후보 | 재생 SDK·유료 접근 제한·계약 기능을 확인한 뒤 선택 |

NestJS, 별도 목 서버, Redis, ORM을 먼저 도입하지 않는다. 필요한 트랜잭션과 영속 작업 기록은 PostgreSQL로 시작한다. 새로운 SDK·실행 환경은 서버 구현 범위가 정해진 뒤 필요한 것만 설치한다.

Next.js API는 브라우저 입력 검증, 세션·권한 확인, 외부 서비스 호출, 화면용 응답 매핑을 맡는다. 민감한 데이터 접근은 `server-only` 코드에 두되, 초기부터 범용 서비스 계층을 만들지 않는다. Route Handler의 요청별 DB 조회에 목 UI용 `use cache` 정책을 덧붙이지 않는다. 설치된 Next.js의 [Route Handler 가이드](../node_modules/next/dist/docs/01-app/01-getting-started/15-route-handlers.md), [데이터 보안 가이드](../node_modules/next/dist/docs/01-app/02-guides/data-security.md)를 기준으로 구현한다.

### 인증·권한의 기본 조건

1. Supabase를 선택하면 요청별 서버 클라이언트와 `@supabase/ssr` 방식을 사용한다. 세션 갱신은 공식 Next.js 지침의 `proxy.ts`와 쿠키 전달 방식에 맞추고, 서버에서 `getSession()` 결과만으로 권한을 승인하지 않는다. 검증된 사용자 식별과 필요한 최신 사용자 조회를 구분한다. [공식 SSR 가이드](https://supabase.com/docs/guides/auth/server-side/creating-a-client?queryGroups=framework&framework=nextjs)
2. 보호 API마다 사용자·대상 소유권을 확인한다. 화면 layout의 로그인 검사만으로 보호하지 않는다. 비공개 사용자 조회는 요청 시점에 수행하고, 세션 갱신 응답과 개인 데이터를 공유 캐시에 넣지 않는다.
3. 외부에 노출되는 DB 스키마는 명시적인 테이블 권한과 RLS를 함께 설정한다. 본인 행의 조회·갱신 조건을 구분하고, 사용자 클라이언트의 주문·결제·이용권 직접 쓰기를 허용하지 않는다. 서버의 비밀 키가 RLS를 우회할 수 있으므로 API 자체의 소유권 검사도 필요하다. [공식 RLS 가이드](https://supabase.com/docs/guides/database/postgres/row-level-security)
4. `?view=admin`, 요청 본문의 사용자 ID, 수정 가능한 `user_metadata`를 권한 근거로 쓰지 않는다. 관리자·금전 관련 권한은 현재 DB 기록으로 확인한다. 강사와 관리자의 권한 차이는 기획에서 확정해야 한다.
5. 비밀 키는 서버 환경에만 둔다. 쿠키 인증을 사용하는 변경 요청은 출처·CSRF 대책, 입력 형식·본문 크기, 요청 제한, 외부 호출 타임아웃을 검증한다. 로그에서 비밀번호·토큰·연락처·결제 원문을 제거한다. [설치된 BFF 가이드](../node_modules/next/dist/docs/01-app/02-guides/backend-for-frontend.md)

## 3. 최소 데이터 구조 제안

| 데이터 묶음 | 필요한 기록 | 지킬 조건 |
| --- | --- | --- |
| 회원 | Auth 사용자 ID, 프로필, 마케팅 동의 변경 기록 | 비밀번호는 자체 DB에 저장하지 않음; 생년월일은 날짜, 연락처는 문자열 |
| 상품·강의 | VOD/PDF 상품, 실제 게시 시각, 판매 상태, 챕터·강의·제공된 후기 | fixture의 배열 순서로 최신순을 결정하지 않음; 제공되지 않은 강의·후기를 생산 데이터로 만들지 않음 |
| 주문·결제·환불 | 구매 당시 상품명·금액·조건 스냅샷, PG 식별자, 처리 상태, 멱등 키와 처리 결과 | 원 단위 정수 금액; 주문·PG 거래·처리 요청 중복 제한; 결제 이후 상품 변경이 과거 주문을 바꾸지 않음 |
| 이용권·수강실 | 소유자, 대상 상품, 시작·만료 시각, 상태, 수강실 숨김 여부 | 확인된 결제로만 이용권 부여; 숨김은 주문·결제·환불 기록을 삭제하지 않음 |
| 학습·파일 이용 | 마지막 재생 위치, 완료 강의, 유료 구간 이용 기록, 파일 제공 기록 | 완료 개수·재생 위치·환불용 이용분을 별도 값으로 관리 |

시각은 UTC로 저장하고 화면에서 KST로 표시한다. 수강 기간의 시작 기준·종료 경계, PDF 다운로드가 이용분에 포함되는 조건, 환불 반올림·정책 버전은 구현 전에 확정한다. 현재 화면 타입은 표시용 DTO이므로 DB 컬럼으로 그대로 복제하지 않는다. 마이그레이션과 개발용 seed는 재현 가능하게 관리하고, Figma 예시 회원·주문을 운영 DB에 넣지 않는다.

### 금전 처리에서 먼저 정할 흐름

**결제·환불 외부 호출과 우리 DB를 하나의 트랜잭션으로 묶을 수 없다.** 처리 요청을 DB에 먼저 기록하고 같은 작업의 재시도에는 동일한 멱등 키를 사용한다. 확인된 PG 결과를 받은 뒤 주문·결제·이용권 갱신을 DB 트랜잭션으로 처리한다.

타임아웃이나 PG 성공 뒤 DB 저장 실패는 새 결제 요청으로 덮지 않는다. 기록한 식별자로 PG 상태를 조회해 복구하고, 미완료 요청을 다시 확인하는 절차를 둔다. 초기에는 수동 복구도 가능하되 담당자·확인 방법·중복 방지 조건을 명시한다. 운영 자동 복구가 필요하면 그때 실행 주기를 정한다. [Toss 멱등 키 지침](https://docs.tosspayments.com/reference/using-api/authorization)

성공 URL의 `paymentKey`, `orderId`, `amount`만으로 성공을 확정하지 않는다. 서버가 저장한 주문 금액·소유권과 대조하고 PG 승인 결과로 확정한다. 웹훅은 중복 수신을 허용하는 구조로 저장하고, 적용할 이벤트의 실제 인증 규약을 확인한 뒤 신뢰할 수 있는 PG 조회 결과와 대조한다. 일반 웹훅에 문서에 없는 서명 규약을 가정하지 않는다. 로컬 `127.0.0.1`은 웹훅 수신 주소로 등록할 수 없으므로 공개 테스트 주소가 필요한 시점에 별도로 준비한다. [결제 연동 지침](https://docs.tosspayments.com/guides/v2/payment-widget/integration), [웹훅 지침](https://docs.tosspayments.com/guides/v2/webhook)

환불 견적에는 주문·실제 결제액·확인된 이용분·적용 정책·유효 기간 또는 버전을 포함하도록 제안한다. 실행 직전에 다시 검증하고, 그사이 학습·다운로드로 금액이 달라지는 경우의 처리와 이용 제한 시점을 먼저 확정한다. 현재 `order-1`의 **99,000원 / 전체 600분 / 중복 제외 60분 / 예상 89,100원**은 Figma 예시다. 이를 모든 주문의 실제 환불 공식으로 확정하거나 완료 강의 비율로 대체하지 않는다. 법적 환불 기준의 적합성은 이 기술 초안에서 검증하지 않았다.

## 4. 현재 목 경로와 실제 API 전환 제안

다음 경로는 초기 제안이다. 로그인 사용자와 권한은 서버가 결정하고, UI 검토용 `state`·`view` 쿼리는 실제 서버 권한이나 주문 상태로 받아들이지 않는다.

| 현재 목 조회 | 실제 조회 경로 제안 | 응답 범위·보호 조건 |
| --- | --- | --- |
| `/__mock/products` | `GET /api/products` | 공개 판매 목록·정렬·개수 |
| `/__mock/products/:slug` | `GET /api/products/:slug` | 상품 상세; 소유·관리 가능 여부는 검증된 사용자 기준 |
| `/__mock/profile` | `GET /api/profile` | 본인 프로필만 반환 |
| `/__mock/classroom` | `GET /api/classroom` | 본인 이용권과 수강실 표시 상태 |
| `/__mock/courses/:courseId` | `GET /api/classroom/courses/:courseId` | 유효 이용권 검사 후 시청실 표시 데이터 |
| `/__mock/orders` | `GET /api/orders` | 본인 주문과 확정된 처리 상태 |
| `/__mock/orders/:orderId/refund` | `GET /api/orders/:orderId/refund-quote` | 본인 주문의 구조화된 금액·이용분·정책; 화면 문구로 매핑 |

`/__mock/auth-state`는 디자인 상태 검토용이다. 실제 인증 API로 그대로 바꾸지 않는다. 실제 인증은 선택한 Auth의 가입·로그인·로그아웃·복구 절차로 연결한다.

변경 요청은 다음 다섯 묶음에서 필요한 API만 정한다. 아직 구현할 전체 API 명세가 아니다.

1. 인증·프로필: 실제 세션, 복구 링크 검증 후 비밀번호 변경, `PATCH /api/profile`, 소유자가 제한된 이미지 업로드.
2. 상품 관리: 기획에 명시된 관리자 작업만 연결. 미제공 `/manage/courses/...` 편집 화면은 먼저 디자인·권한 범위 확인.
3. 결제: 주문 생성, PG 승인 확인, 웹훅 처리. 결제액을 브라우저 값으로 확정하지 않음.
4. 학습: 진도 저장, 파일 접근 발급, 수강실 숨김. 구매 기록 삭제로 구현하지 않음.
5. 환불: 견적 확인과 환불 신청·결과 저장. 중복 요청·금액 변경·PG 처리 후 DB 실패를 처리.

### 실제 연결 시 수정할 기존 위치

| 위치 | 최소 수정 |
| --- | --- |
| `src/app/providers.tsx`, `src/app/mock-initializer.tsx` | 목 모드와 실제 API 모드를 분리. 현재 운영 환경에서는 `useMockReady()`가 계속 false이므로 URL 변경만으로 조회가 실행되지 않음. 실제 모드 조회는 worker 준비 조건과 분리 |
| `src/features/catalog/api.ts`, `src/features/classroom/api.ts` | 조회 URL·입력·응답 매핑 조정; 화면 표시 타입은 가능한 한 유지 |
| `src/features/account/use-profile.ts`, `src/features/account/orders-api.ts` | 실제 보호 API 연결; 로그인 사용자별 Query 캐시 구분·로그아웃 시 개인 캐시 제거; 저장 후 프로필·헤더 조회 갱신 |
| `src/features/auth/auth-form.tsx` | 필드 검증 이후 실제 인증 결과 연결; 확인된 결과에 맞춰 기존 디자인 상태 표시 |
| `src/mocks/*.ts` | 개발 목 모드에서만 유지; 실제 API 검증에서는 MSW를 끄고 요청 출처·DB 결과를 확인 |

실제 모드에서도 전체 앱을 Client Component로 바꾸지 않는다. 동적 인증 표시가 필요한 경계만 분리하고 기존 Server Component를 유지한다. 서버와 브라우저의 QueryClient·인증 클라이언트를 사용자 간 공유하지 않는다.

완료 화면은 현재처럼 UI 직접 검토에 사용할 수 있다. 서비스 모드에서는 가입·결제 완료를 경로 진입만으로 주장하지 않고 실제 상태를 조회해 표시한다. 직접 진입 가능한 검토 상태와 서비스 상태를 구분해야 한다.

## 5. 먼저 확인할 인증·파일·영상 조건

| 항목 | 확인·검증할 조건 |
| --- | --- |
| 가입·비밀번호 | 현재 UI에는 서버의 비밀번호 강도·이메일 확인 정책이 확정되어 있지 않음. Auth 설정과 디자인 문구를 맞춤. Auth 사용자 생성 뒤 프로필 저장이 실패한 경우 재시도로 복구 |
| 비밀번호 찾기 | Figma의 이메일·이름·연락처 확인과 회원 없음 문구는 Auth 기본 복구의 계정 존재 비공개 정책과 충돌할 수 있음. 공개 정책을 결정하고 시도 제한 적용. 이름·연락처 일치만으로 비밀번호 변경 허용 금지 |
| 메일 | 운영용 SMTP 선택·발신 주소·복구 URL 필요. 기본 Supabase SMTP는 제한된 테스트용이며 공개 서비스용으로 가정하지 않음. 개발 메일 수신 도구로 만료·재사용·다른 사용자 링크를 검증 |
| 프로필·PDF | 프로필 파일의 실제 형식·디코딩·5MiB 제한을 서버에서도 검증. 브라우저 blob URL 대신 소유권이 있는 저장 경로 사용. 유료 PDF는 private 저장소에서 이용권 확인 후 제공 |
| 영상·이용분 | Vimeo 계약 기능으로 유료 접근 제한이 가능한지 확인. 마지막 위치·강의 완료와 환불 이용분을 구분. 무료 미리보기·탐색 이동·반복 시청 처리 기준 확정 |

Supabase의 복구 요청은 기본적으로 존재하지 않는 계정을 에러로 알려주지 않는다. 복구 토큰 또는 검증된 복구 세션을 확인한 뒤 비밀번호를 바꾼다. [비밀번호 인증 지침](https://supabase.com/docs/guides/auth/passwords), [운영 SMTP 지침](https://supabase.com/docs/guides/auth/auth-smtp)

큰 파일은 호스팅의 요청 크기 제한을 확인해 직접 업로드 방식도 검토한다. 파일 검사·소유권 확인을 통과한 뒤 프로필 참조를 바꾸고, 기존 파일 정리는 저장 성공 이후에 한다. 유료 파일의 signed URL은 발급 이후 만료 시각까지 유효하므로 환불·이용권 취소만으로 즉시 회수된다고 주장하지 않는다. 짧은 TTL과 인증 다운로드 중 접근 정책에 맞는 방식을 선택하며, 이미 내려받은 파일은 회수할 수 없다. [Storage 다운로드 지침](https://supabase.com/docs/guides/storage/serving/downloads)

Vimeo SDK의 `progress`는 버퍼 진행이고 `timeupdate`에는 탐색 이동도 섞일 수 있다. 최대 재생 위치를 시청 시간으로 계산하지 않는다. 유료 구간 중복 제외 집계와 서버 검증 범위를 정하되, 브라우저 이벤트만으로 금전 처리의 증빙이 완성된다고 가정하지 않는다. 필요한 신뢰도를 공급자 기능과 함께 확인한다. [Vimeo 공식 SDK](https://github.com/vimeo/player.js)

## 6. 서버 개발 묶음 순서

| 순서 | 묶음 | 완료 조건 |
| --- | --- | --- |
| 1 | 환경·목/실제 모드 → 인증 → 프로필 | 실제 로그인·세션 만료·로그아웃, 사용자 A/B 분리, 본인 프로필 조회·저장·실패 복구; 메일 테스트 |
| 2 | 공개 상품·상세 → 관리자 권한 | 실제 DB 목록·정렬·상세, 판매 상태; 쿼리 변조로 관리자 권한 획득 불가 |
| 3 | 테스트 결제 → 주문 → 이용권 | 테스트 PG 확인 결과와 DB 일치, 중복 승인 방지, 타임아웃·PG 성공 후 DB 실패 복구 |
| 4 | 수강실 → 비공개 PDF → 영상·진도 | 본인 이용권·만료 검사, 접근 발급, 숨김 보존, 탐색·반복·무료 구간 검증 |
| 5 | 환불 견적 → 신청·취소 확인 | 확정 정책의 금액, 동시 이용·중복 신청·외부 성공 뒤 저장 실패 검증; 전체 PC 회귀 확인 |

각 묶음은 한 번에 전체를 구현하지 않는다. 예를 들어 묶음 1은 환경 모드 분리, 인증 세션, 보호 프로필 GET, 프로필 PATCH를 각각 검증하고 진행한다. 미정 UI·외부 서비스 조건 때문에 막힌 항목만 보류하고 독립 작업은 계속한다.

## 7. dev-loop 운영 초안

현재 사용자가 승인한 PC 범위에서는 화면마다 재승인을 요청하지 않는다. 새 화면·미정 디자인·정해지지 않은 서버 정책은 승인된 것으로 추측하지 않는다. 초안 작성 요청을 서버 구축 승인으로 확대하지 않는다.

1. **조사:** 기존 파일·staged/unstaged diff·untracked 파일·실행 상태를 확인한다. 재개 시 마지막 대화 상태표와 실제 코드를 대조한다. 사용자 변경, 기존 브랜치, 프로젝트 설정을 보존한다.
2. **작업 단위 확정:** API 하나와 연결 화면 하나를 기준으로 입력·응답·소유권·실패 조건·완료 근거를 정한다. 목 UI와 실제 연동 중 이번 검증 모드를 먼저 밝힌다.
3. **최소 구현:** 필요한 DB 변경·API·조회 함수·화면 연결만 수정한다. 실제 응답 전 성공을 표시하지 않는다. 관련 export·호출자·fixture를 함께 확인한다.
4. **검증:** 요청 결과와 DB·외부 테스트 서비스의 실제 상태를 대조한다. PC 라우트 직접 진입·조작·브라우저 오류·네트워크·스크린샷을 확인하고, 변경 위험에 맞는 최소 자동 검증을 수행한다.
5. **수정·기록:** 실패 단위, 기대/실제, 재현 로그, 원인 가설을 대화에 기록한다. 한 가설의 최소 수정 후 같은 조건으로 재검증한다. 같은 실패의 수정은 최대 3회이며 개선이 없으면 의심 가정과 진단 질문 하나를 남긴다.

승인·정보·접근 문제를 코드 수정 횟수로 계산하지 않는다. 별도 계획·상태 파일, 리뷰 JSON, 서브에이전트, 정기 자동화, 새 브랜치·worktree는 자동으로 추가하지 않는다. 커밋·배포는 해당 작업의 사용자 지시에 따른다.

### 검증 구분

| 종류 | 근거 | 통과로 주장할 수 없는 것 |
| --- | --- | --- |
| MSW UI | 실제 handler 처리와 fixture 표시, 명시된 빈/오류 상태, PC 조작 | 인증·저장·실제 결제·환불 성공 |
| 실제 테스트 연동 | MSW 비활성, 실제 API 응답·DB 기록·메일/PG 테스트 결과 | 운영 서비스 검증·실제 매출 |
| 운영 배포 | 별도 승인 후 운영 설정·권한·모니터링·복구 확인 | 빌드 성공만으로 운영 완료 |

보호 API는 최소 두 사용자로 A가 B의 프로필·주문·이용권·파일을 읽거나 바꿀 수 없는지 확인한다. DB 직접 접근이 노출된 경로에는 RLS도 검증한다. 로그아웃·세션 만료·사용자 전환 뒤 이전 사용자 데이터가 Query 캐시에서 나타나지 않아야 한다.

로직 검증은 금액 계산·중복 방지·권한·복구처럼 회귀 위험이 있는 부분에 집중한다. 문서·단순 스타일 변경 때문에 테스트 프레임워크를 설치하지 않는다. 묶음 종료 시 현재 scripts에 맞춰 아래 검사를 수행하고, 공통 코드 변경은 영향을 받는 이전 화면도 확인한다.

```bash
npm run lint
npx next typegen
npx tsc --noEmit
npm run build
```

| 작업 단위 | 현재 단계·UI 상태 / 서버 연동 상태 | 승인 범위·미정 사항 | 검증 근거·수정 횟수 | 다음 단계 |
| --- | --- | --- | --- | --- |
| 예: 본인 프로필 GET | 실제 API 검증 진행 중 / 연동 대기 | PC 기존 화면; 인증·DB 선택 필요 | 실제 사용자 A/B·401·DB 대조 결과 기록 / 0회 | 통과 후 저장 요청 |

## 8. 구현 전 결정할 항목

1. **환경:** Next.js 호스팅·리전·예산, Supabase 사용 여부와 개발/운영 분리.
2. **인증:** 이메일 확인·비밀번호 정책·복구의 회원 존재 공개 정책, 이름·연락처 확인 역할, 운영 SMTP.
3. **결제:** PG 선택·테스트 자격 정보·결제 수단·결제창 동선과 필요한 약관 디자인.
4. **수강·환불:** 이용권 시작·만료 경계, Vimeo 접근 제한, 완료·유료 이용분·다운로드의 정의, 금액 반올림·동시 이용·환불 실행 정책.
5. **UI·권한:** 남은 PC 디자인 기준, 관리자와 강사 구분, 미제공 관리 화면 범위.

첫 서버 실행 단위는 **확정한 환경의 인증 세션 기반 → 본인 프로필 GET**을 추천한다. 이 단위에서 실제 모드 조회와 사용자 분리를 먼저 입증한 뒤 상품·결제로 확장한다.
